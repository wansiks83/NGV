# ISO 25010 기반 비기능 요구사항 작성 가이드

> 이 파일의 품질특성 분류표는 이 프로젝트에서 ISO 25010/25000(SQuaRE) 품질특성을 사용하는 **원본 정의**다. `sw-system-test` 스킬이 비기능 테스트 케이스를 품질특성별로 그룹화할 때 이 표를 그대로 참조하며, 별도로 다시 정의하지 않는다.

## ISO 25010 품질특성 8가지와 부특성

| 품질특성 | 주요 부특성 | 비기능 요구사항 예시 |
|---|---|---|
| 기능적합성 | 완전성, 정확성, 적절성 | 입력값 범위 내에서 계산 오차는 ±0.5% 이내여야 한다 |
| 성능효율성 | 시간반응성, 자원사용성, 용량 | 요청 접수부터 응답까지 100ms 이내여야 한다 |
| 호환성 | 공존성, 상호운용성 | 다른 ECU와 CAN 통신 시 정의된 메시지 포맷을 준수해야 한다 |
| 사용성 | 인식적합성, 학습성, 운용성, 오류방지성, 접근성 | 초기 사용자가 5분 내 주요 기능을 오류 없이 수행할 수 있어야 한다 |
| 신뢰성 | 성숙성, 가용성, 결함허용성, 회복성 | 평균 고장 간격(MTBF)이 정의된 값 이상이어야 한다 |
| 보안성 | 기밀성, 무결성, 부인방지성, 책임추적성, 인증성 | 인증되지 않은 요청은 100% 거부해야 한다 |
| 유지보수성 | 모듈성, 재사용성, 분석용이성, 수정용이성, 시험용이성 | 순환복잡도가 정의된 임계값을 초과하지 않아야 한다 |
| 이식성 | 적응성, 설치성, 대체성 | 정의된 타깃 플랫폼에서 재컴파일만으로 동작해야 한다 |

## 작성 규칙

1. 비기능 요구사항 하나마다 위 표의 품질특성/부특성 중 하나 이상을 명시한다.
2. 요구사항 문장은 반드시 측정 가능한 수치·조건을 포함한다. "빠르게", "안정적으로", "충분히" 같은 정성적 표현만으로 끝내지 않는다.
3. 수치 기준은 근거(상위 요구사항, 이해관계자 합의, 벤치마크 등)를 함께 밝힌다. 근거 없는 임의 수치를 제시하지 않는다.

## 실행 가능한 검증방안 수립 기준

검증방안은 아래 네 가지 방법 중 하나 이상으로 제시한다.

- **시험**: 실제 환경 또는 시험 환경에서 값을 측정하여 기준과 비교한다.
- **분석**: 계산·시뮬레이션·정적분석으로 값을 산출하여 기준과 비교한다.
- **검사**: 설계 문서·코드·설정을 사람이 검토하여 기준 충족 여부를 판단한다.
- **시연**: 정해진 시나리오를 실행하여 관찰 가능한 결과로 기준 충족 여부를 보여준다.

검증방안이 실행 가능하려면 다음을 모두 만족해야 한다.

- 이 프로젝트가 실제로 보유했거나 확보 가능한 도구·장비·환경으로 수행 가능하다.
- 합격/불합격을 가르는 기준값과 측정 방법이 구체적으로 정의되어 있다.
- 측정 방법이 재현 가능하다(같은 조건이면 같은 결과가 나온다).
- 검증에 필요한 전제조건(테스트 데이터, 시험 장비, 특수 환경 등)이 현실적으로 준비 가능하다.

다음과 같은 검증방안은 실행 불가능한 것으로 보고 제시하지 않는다.

- "충분히 안정적임을 확인한다"처럼 판정 기준이 없는 경우.
- 무한하거나 비현실적으로 큰 입력 공간을 전수 검사하겠다는 경우(예: "모든 가능한 입력에 대해 수동 검토").
- 존재하지 않거나 확보 계획이 없는 도구/장비/데이터를 전제로 하는 경우.
- 측정 자체가 요구사항이 정의한 조건과 동일하지 않아 기준과 비교할 수 없는 경우.

검증방안을 실행 가능하게 만들 수 없다면, 요구사항 자체(수치·조건)를 검증 가능한 형태로 다시 쓰는 방안을 함께 제안한다.

## 예시

- **요구사항(NFR)**: `SW-REQ-030 성능효율성 — 제동 명령 산출 로직은 센서 데이터 수신 후 20ms 이내에 제동 명령을 출력해야 한다.`
- **검증방안**: `시험 — 시험 벤치에서 센서 입력 신호를 주입한 시점부터 제동 명령 출력 시점까지의 시간을 오실로스코프로 100회 측정하며, 최댓값이 20ms를 초과하지 않아야 합격으로 판정한다.`
