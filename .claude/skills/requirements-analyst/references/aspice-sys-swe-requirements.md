# A-SPICE 4.1 — SYS.2 / SWE.1 요구사항 분석 프로세스

## SYS.2 — 시스템 요구사항 분석

**목적**: 이해관계자 요구사항을 분석하여, 검증 가능한 시스템 요구사항으로 변환한다.

**기본수행항목(BP) 요약**
- 이해관계자 요구사항으로부터 시스템 요구사항을 명세한다.
- 요구사항을 구조화한다.
- 요구사항의 정확성·기술적 타당성을 분석한다.
- 요구사항 변경의 영향(안전성, 비용, 일정, 다른 요구사항)을 분석한다.
- 각 시스템 요구사항에 대한 검증 기준을 정의한다.
- 이해관계자 요구사항 ↔ 시스템 요구사항 간 양방향 추적성과 일관성을 확보한다.
- 이해관계자와 합의를 도출하고 의사소통한다.

**산출물 후보**
- 시스템 요구사항 명세서
- 이해관계자 요구사항 ↔ 시스템 요구사항 추적표
- 시스템 요구사항별 검증 기준

## SWE.1 — 소프트웨어 요구사항 분석

**목적**: 시스템 요구사항 중 소프트웨어에 할당된 부분과 인터페이스를 분석하여, 일관되고 검증 가능한 소프트웨어 요구사항을 도출한다.

**기본수행항목(BP) 요약**
- 소프트웨어 요구사항을 명세한다.
- 요구사항을 구조화한다.
- 요구사항의 정확성·기술적 타당성을 분석한다.
- 요구사항 변경의 영향을 분석한다.
- 각 요구사항에 대한 검증 기준을 정의한다.
- 시스템 요구사항 ↔ 소프트웨어 요구사항 간 양방향 추적성과 일관성을 확보한다.
- 이해관계자와 합의를 도출하고 의사소통한다.

**산출물 후보**
- 소프트웨어 요구사항 명세서
- 시스템 요구사항 ↔ 소프트웨어 요구사항 추적표
- 소프트웨어 요구사항별 검증 기준

## 계층 간 추적성 원칙

이해관계자 요구사항 → 시스템 요구사항(SYS.2) → 소프트웨어 요구사항(SWE.1) → (이후 SWE.2 아키텍처, SWE.4/5/6 검증) 까지 양방향 추적이 가능해야 한다. 요구사항 분석 단계에서는 최소한 다음을 확보한다.

- 모든 시스템/소프트웨어 요구사항은 상위 출처(이해관계자 요구사항 또는 상위 시스템 요구사항, 또는 ISO 26262 안전목표)를 명시한다.
- 상위 요구사항 하나에 대응하는 하위 요구사항이 없거나, 하위 요구사항에 대응하는 상위 요구사항이 없는 경우 갭으로 기록한다.
- 요구사항 변경 시 추적표를 함께 갱신한다.

## 요구사항 속성 (공식 문구가 아닌 요약)

각 요구사항은 최소한 다음 속성을 가진다: 고유 ID, 설명, 유형(기능/비기능), 출처, 우선순위, ASIL(해당 시), 검증방법, 상태, 추적 링크. 정확한 조문이 필요하면 공식 PAM 4.1 문서를 확인해야 한다.
