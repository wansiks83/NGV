# 요구사항 분석가 (시스템/소프트웨어 요구사항, ISO 26262 + A-SPICE)

## 이 스킬을 사용하는 시점

시스템 요구사항(A-SPICE SYS.2) 또는 소프트웨어 요구사항(A-SPICE SWE.1)을 새로 도출·작성하거나, 기존 요구사항을 ISO 26262/A-SPICE/ISO 25010 관점에서 점검·보완할 때 사용한다.

## 0단계 — 사용자 템플릿 확인 (반드시 가장 먼저)

요구사항 산출물은 **반드시 사용자가 제시한 템플릿**을 따라야 한다.

1. 이 스킬 폴더의 `templates/requirement-template.md`를 읽는다. 안내 주석만 있고 실제 템플릿 내용이 없다면 사용자가 아직 템플릿을 제공하지 않은 것이다.
2. 혹시 사용자가 이 파일이 아닌 다른 경로(`templates/`, `docs/templates/` 등, 파일명에 "template"·"템플릿"·"양식" 포함)에 템플릿을 두었을 수도 있으니 저장소 전체를 한 번 더 검색한다.
3. 템플릿을 어디에서도 찾을 수 없으면, **작업을 진행하지 말고 사용자에게 템플릿을 요청**한다. 임의로 템플릿 형식을 추측해서 만들어내지 않는다. 사용자가 "템플릿 없이 임시로 진행해달라"고 명시적으로 말한 경우에만, 그 사실을 산출물 최상단에 "※ 정식 템플릿 미적용 — 추후 템플릿 적용 시 재구성 필요"라고 명시하고 이 스킬의 기본 구조(아래 "출력 구조 기본값" 참고)로 진행한다.
4. 템플릿을 찾으면, 이후 모든 산출물은 이 스킬이 정의한 기본 구조가 아니라 **그 템플릿의 항목·순서·표기법을 그대로 따른다.**

## 1단계 — 요구사항 도출 및 분류

- 입력(시스템 콘텍스트, 이해관계자 니즈, 상위 요구사항, 안전목표 등)으로부터 요구사항을 도출한다.
- 각 요구사항을 **기능 요구사항(FR)**과 **비기능 요구사항(NFR)**으로 분류한다.
- 시스템 요구사항(SYS.2)과 소프트웨어 요구사항(SWE.1)을 구분하고, 상위(시스템) ↔ 하위(소프트웨어) 요구사항 간 양방향 추적성을 확보한다. 세부 프로세스 매핑은 `references/aspice-sys-swe-requirements.md` 참고.

## 2단계 — 기능 요구사항: UML/SysML 다이어그램화

기능 요구사항은 텍스트만으로 끝내지 않고, 요구사항의 성격에 맞는 UML/SysML 다이어그램을 함께 제시한다. 다이어그램 선택 기준과 표기법, PlantUML 예시는 `references/uml-sysml-guide.md` 참고. 다이어그램은 반드시 해당 요구사항 ID와 연결(참조)한다.

## 3단계 — 비기능 요구사항: ISO 25010 기반 작성 + 실행 가능한 검증방안

- 모든 비기능 요구사항을 ISO 25010의 8개 품질특성(기능적합성, 성능효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성) 중 해당하는 특성/부특성에 명시적으로 매핑한다.
- 각 비기능 요구사항은 **측정 가능한 수치 기준**(예: 응답시간 ≤ 100ms)으로 작성한다. "충분히 빨라야 한다", "안정적이어야 한다" 같은 정성적 문장만으로 끝내지 않는다.
- 각 비기능 요구사항마다 **검증방안**을 함께 제시한다. 검증방안은 시험/분석/검사/시연 중 하나 이상이어야 하며, 아래 조건을 만족해야 실행 가능한 것으로 인정한다:
  - 현재 프로젝트의 기술/도구/환경으로 실제 수행 가능해야 한다(무한 자원, 존재하지 않는 도구, 불가능한 조건을 전제로 하지 않는다).
  - 통과/실패 판정 기준이 명확해야 한다(합격 기준이 수치·조건으로 정의되어야 한다).
  - "만족스러움을 확인한다"처럼 판정 주체·기준이 불명확한 검증방안은 제시하지 않는다.
  - 검증방안이 실행 불가능하다고 판단되면, 요구사항 자체의 수치·조건을 검증 가능한 수준으로 재작성할 것을 함께 제안한다.
  - 세부 가이드와 예시는 `references/iso25010-nfr.md` 참고.

## 4단계 — ISO 26262 준수

- 안전 관련 요구사항에는 안전목표/ASIL을 상위 요구사항으로부터 상속하여 명시한다.
- 요구사항 속성(ID, 출처, ASIL, 상태, 검증방법 등)을 빠짐없이 기재한다.
- 세부 기준은 `references/iso26262-requirements.md` 참고.

## 5단계 — 명확성과 일관성 확보

작성이 끝나면 반드시 `references/quality-checklist.md`의 체크리스트로 모든 요구사항을 자체 점검한다. 특히:
- **명확성**: 하나의 요구사항에는 하나의 요구사항만 담는다(원자성). 애매한 대명사·복수 해석 가능한 표현·업계 은어를 피하고, 사람이 배경지식 없이 읽어도 같은 의미로 이해되도록 쓴다.
- **일관성**: 같은 대상을 가리키는 용어를 요구사항 전체에서 통일한다. 다른 요구사항과 모순되지 않는지, 상위 요구사항과 어긋나지 않는지 상호 대조한다.

## 출력 구조 기본값 (사용자 템플릿이 없을 때만 임시로 사용)

| 항목 | 내용 |
|---|---|
| 요구사항 ID | 예: SYS-REQ-001, SW-REQ-001 |
| 유형 | 기능(FR) / 비기능(NFR) |
| 설명 | 원자적이고 명확한 문장 |
| 출처/상위 요구사항 | 상위 요구사항 ID, 이해관계자 니즈 등 |
| ASIL / 안전목표 | 해당 시 기재, 해당 없으면 QM |
| ISO 25010 특성 (NFR만) | 해당 품질특성/부특성 |
| 다이어그램 (FR만) | UML/SysML 다이어그램 종류 + 참조 |
| 검증방안 | 시험/분석/검사/시연 중 실행 가능한 방법 + 합격 기준 |
| 추적성 | 상위/하위 요구사항, 테스트케이스 ID |
| 상태 | 초안/검토중/승인 |
