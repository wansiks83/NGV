# 아키텍처 설계자 (소프트웨어 아키텍처, ISO 26262 Part 6 + A-SPICE SWE.2)

## 이 스킬을 사용하는 시점

소프트웨어 요구사항(SWE.1 산출물)으로부터 소프트웨어 아키텍처(A-SPICE SWE.2)를 설계하거나, 기존 아키텍처를 응집력/결합도/SOLID/인터페이스/통합순서 관점에서 점검·보완할 때 사용한다.

## 0단계 — 산출물 양식 확인 (반드시 가장 먼저)

이 저장소에는 이미 실제 아키텍처 설계서 양식이 있다. 임의로 형식을 만들지 않고 아래 파일을 그대로 사용한다.

- 본문 양식: `WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-001_SW 아키텍처 설계서 템플릿.docx` — 15개 절(목적/적용범위, 아키텍처 설계 원칙, 논리 아키텍처[요소/관계와 제약], 컴포넌트 책임, 정적 의존성, 인터페이스 명세[내부/외부], 동적 동작, 상태 전이, 오류 격리와 안전 동작, 품질속성 분석, 통합 전략, 요구사항 할당, 자원 및 배포 경계, 추적성, 참고자료) 구조를 그대로 따른다.
- 다이어그램 양식: `WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-002_SW 아키텍처 UML 템플릿.drawio`.

위 경로에서 파일을 찾지 못하면(이동·삭제된 경우) 저장소 전체를 검색하고, 그래도 찾지 못하면 임의로 형식을 만들지 말고 사용자에게 요청한다. 사용자가 "양식 없이 임시로 진행해달라"고 명시한 경우에만 아래 "출력 구조 기본값"으로 진행하고, 그 사실을 산출물 최상단에 명시한다.

`TPL-SWE2-001`의 절 구성은 이 스킬의 단계와 다음처럼 대응한다: 2절(아키텍처 설계 원칙)↔3단계, 3~6절(논리 아키텍처/컴포넌트 책임/정적 의존성/인터페이스 명세)↔4~5단계, 7~8절(동적 동작/상태 전이)↔3~4단계, 9절(오류 격리와 안전 동작)↔ASIL 간섭으로부터의 자유, 11절(통합 전략)↔5단계, 12절(요구사항 할당)·14절(추적성)↔6단계.

## 1단계 — 입력 확인

- SWE.1 소프트웨어 요구사항(및 필요 시 시스템 요구사항, ASIL 정보)을 확인한다. 없으면 사용자에게 위치를 확인한다.
- 시스템 제약(하드웨어 플랫폼, 실시간성 요구, 기존 자산/레거시 컴포넌트 등)을 확인한다.

## 2단계 — 후보 아키텍처 구조 제안 (사용자가 선택하기 전까지 확정하지 않음)

아키텍처를 하나로 확정해 밀어붙이지 않는다. `references/architecture-patterns.md`를 참고하여 이 시스템의 요구사항·제약에 맞는 **2~4개의 후보 아키텍처 구조**를 각각 다음 정보와 함께 제시한다.

- 구조 이름과 핵심 아이디어
- 이 시스템에 적용했을 때의 장점
- 이 시스템에 적용했을 때의 단점/트레이드오프
- 이 구조를 선택했을 때 응집력/결합도/변경 유연성에 미치는 영향

제시한 뒤에는 **반드시 사용자의 선택을 기다린다.** 사용자가 고르기 전까지 3단계 이후로 진행하지 않는다.

## 3단계 — 아키텍처 설계 원칙 적용

선택된 구조를 아래 원칙에 따라 구체화한다.

- **높은 응집력·낮은 결합도**: 하나의 컴포넌트는 하나의 책임/관심사에 집중시키고(응집력), 컴포넌트 간 의존은 최소화·단방향화한다(결합도). 근거와 점검 방법은 `references/cohesion-coupling.md` 참고.
- **변경 유연성**: 변경이 예상되는 지점(가변점)을 식별하고, 그 지점을 인터페이스/확장점으로 분리해 변경이 국소화되도록 설계한다.
- **SOLID 원칙**: 각 컴포넌트/클래스 설계에 SRP·OCP·LSP·ISP·DIP를 적용한다. 상세 가이드와 적용 예시는 `references/solid-principles.md` 참고.
- **ISO 26262 Part 6 아키텍처 원칙 및 A-SPICE SWE.2**: `references/iso26262-part6-architecture.md`, `references/aspice-swe2.md` 참고. ASIL이 다른 컴포넌트 간에는 간섭으로부터의 자유를 어떻게 확보할지 명시한다.

## 4단계 — 인터페이스 정의 (필수)

- 식별된 모든 컴포넌트에 대해 인터페이스를 정의한다. 컴포넌트는 **반드시 인터페이스를 통해서만** 통신하며, 다른 컴포넌트의 내부 상태·데이터에 직접 접근하지 않는다.
- 각 인터페이스는 최소한 다음을 포함한다: 제공하는 연산/데이터, 입출력 파라미터와 자료형, 사전/사후조건, 오류/예외 처리 방식, 시간 제약(해당 시).
- 세부 작성 방법은 `references/interface-definition-guide.md` 참고.

## 5단계 — 컴포넌트 통합 순서 정의

- 컴포넌트 간 의존관계(누가 누구의 인터페이스를 필요로 하는가)를 근거로 통합 순서를 정의한다.
- 통합 전략(상향식/하향식/점진적/위험기반 등) 중 이 아키텍처에 적합한 전략을 선택하고 근거를 밝힌다.
- 세부 가이드는 `references/integration-order.md` 참고. 이 결과는 이후 A-SPICE SWE.5(소프트웨어 통합) 산출물의 입력으로 이어진다.

## 6단계 — 검증 및 산출물 정리

- 각 아키텍처 요소에 대한 검증 기준(어떻게 이 아키텍처 결정이 지켜졌는지 확인할지)을 정의한다.
- SWE.1 소프트웨어 요구사항 ↔ 아키텍처 요소 간 양방향 추적표를 작성한다.
- 확인된 사용자 양식(또는 승인된 임시 기본 구조)에 맞춰 최종 산출물을 정리한다.

## 출력 구조 기본값 (사용자 양식이 없을 때만 임시로 사용)

| 항목 | 내용 |
