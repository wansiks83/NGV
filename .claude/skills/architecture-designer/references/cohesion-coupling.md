# 응집력·결합도 점검 가이드

측정 도구 없이도 아키텍처 설계 단계에서 점검할 수 있는 실무적 체크리스트다.

## 응집력(컴포넌트 내부) 점검

- [ ] 컴포넌트의 책임을 한 문장으로 설명할 수 있는가(설명에 "그리고"가 들어가면 책임이 두 개 이상일 가능성이 높다).
- [ ] 컴포넌트 내부의 모든 기능이 같은 데이터·같은 목적을 다루는가.
- [ ] 이 컴포넌트를 수정해야 하는 이유(요구사항 변경, 알고리즘 변경, 인터페이스 변경 등)를 나열했을 때, 서로 관련 없는 이유가 섞여 있지 않은가.

## 결합도(컴포넌트 사이) 점검

- [ ] 컴포넌트 A가 컴포넌트 B의 내부 데이터·내부 상태에 직접 접근하지 않는가(반드시 B의 인터페이스를 통해서만 접근해야 한다).
- [ ] 두 컴포넌트가 서로를 직접 참조하는 순환 의존이 없는가(순환 의존은 결합도를 높이고 독립적 교체·시험을 불가능하게 만든다).
- [ ] 하나의 컴포넌트를 교체하려면 몇 개의 다른 컴포넌트를 함께 고쳐야 하는지 추정해 보았는가(많을수록 결합도가 높다).
- [ ] 컴포넌트 간 데이터 교환이 잘 정의된 인터페이스(함수 호출, 메시지, 이벤트 등)로만 이루어지는가, 아니면 전역변수·공유 메모리를 통해 암묵적으로 이루어지는가.
- [ ] 한 컴포넌트의 내부 구현(자료구조, 알고리즘)을 바꿔도 인터페이스만 유지하면 다른 컴포넌트를 고치지 않아도 되는가.

## 결합도 유형 (낮은 것부터 높은 것 순)

낮은 결합도부터 순서대로 나열한다. 설계 시 가능하면 목록 위쪽(낮은 결합도)을 지향한다.

1. 데이터 결합 — 필요한 데이터만 인터페이스의 파라미터로 전달
2. 스탬프 결합 — 필요한 것보다 큰 자료구조(레코드 전체 등)를 전달
3. 제어 결합 — 상대의 내부 동작을 제어하는 플래그/코드를 전달
4. 외부 결합 — 공유된 외부 형식(파일 포맷, 통신 프로토콜)에 의존
5. 공통 결합 — 전역변수·공유 메모리를 통해 상태를 공유
6. 내용 결합 — 다른 컴포넌트의 내부 구현을 직접 참조/수정

공통 결합·내용 결합이 발견되면 반드시 인터페이스를 통한 데이터/제어 결합으로 재설계한다.

## 변경 유연성 점검

- [ ] 요구사항 중 향후 변경 가능성이 높다고 명시되었거나 이해관계자가 언급한 항목을 식별했는가.
- [ ] 그 변경 지점이 하나의 컴포넌트/인터페이스 안에 국소화되어 있는가, 아니면 여러 컴포넌트에 걸쳐 있는가.
- [ ] 변경 지점이 여러 컴포넌트에 걸쳐 있다면, 인터페이스를 추가해 국소화할 수 있는지 재검토했는가.
