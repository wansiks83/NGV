# SOLID 원칙 적용 가이드 (컴포넌트/클래스 설계)

아키텍처의 각 컴포넌트와 그 내부 클래스/모듈 설계에 아래 다섯 원칙을 적용하고, 위반 시 어떤 문제가 생기는지 함께 점검한다.

## 단일 책임 원칙 (하나의 컴포넌트는 하나의 변경 이유만 가져야 한다)

- 컴포넌트를 바꿔야 하는 이유가 두 가지 이상이면 분리 대상이다.
- 점검 질문: "이 컴포넌트를 수정해야 하는 상황을 모두 나열했을 때, 서로 무관한 이유가 섞여 있는가?"

## 개방-폐쇄 원칙 (확장에는 열려있고, 수정에는 닫혀있어야 한다)

- 새로운 변형(새 센서 종류, 새 통신 프로토콜 등)을 추가할 때 기존 컴포넌트 코드를 고치지 않고, 인터페이스를 구현하는 새 컴포넌트를 추가하는 것으로 확장 가능해야 한다.
- 아키텍처 설계 시 "변경이 예상되는 지점"을 확장점(인터페이스)으로 미리 분리해 둔다.

## 리스코프 치환 원칙 (하위 구현은 상위 인터페이스의 계약을 어겨서는 안 된다)

- 같은 인터페이스를 구현하는 여러 컴포넌트(예: 여러 센서 드라이버 구현체)는 호출자 입장에서 동일하게 동작해야 한다.
- 인터페이스 명세의 사전/사후조건을 구현체가 더 강하게 요구하거나(사전조건 강화) 더 약하게 보장하면(사후조건 약화) 이 원칙 위반이다.

## 인터페이스 분리 원칙 (사용하지 않는 기능에 의존하게 만들지 않아야 한다)

- 하나의 거대한 인터페이스에 서로 무관한 기능을 몰아넣지 않는다. 사용자(호출 컴포넌트)별로 필요한 기능만 노출하는 여러 개의 작은 인터페이스로 분리한다.
- 점검 질문: "이 인터페이스를 사용하는 각 컴포넌트가 실제로 이 인터페이스의 모든 연산을 사용하는가?"

## 의존성 역전 원칙 (상위 모듈은 하위 모듈의 구체적 구현이 아니라 추상(인터페이스)에 의존해야 한다)

- 정책/로직을 담은 상위 컴포넌트가 특정 하드웨어·라이브러리 구현에 직접 의존하지 않고, 인터페이스에 의존하도록 설계한다. 구체 구현은 인터페이스를 구현하는 형태로 하위에 위치시킨다.
- 이 원칙이 바로 "컴포넌트는 인터페이스로만 통신한다"는 이 스킬의 필수 요구사항의 근거가 된다.

## SOLID와 응집력/결합도의 관계

- 단일 책임 원칙을 지키면 응집력이 높아진다.
- 개방-폐쇄·의존성 역전 원칙을 지키면 결합도가 낮아지고, 변경이 국소화된다(변경 유연성 확보).
- 리스코프 치환·인터페이스 분리 원칙은 인터페이스 계약의 신뢰성을 보장해, 컴포넌트를 교체·재사용하기 쉽게 만든다.

아키텍처 설계서에는 각 컴포넌트/인터페이스 설계 결정에 대해 위 다섯 원칙 중 어떤 것을 근거로 그렇게 설계했는지 한 줄씩 밝히는 것을 권장한다.
