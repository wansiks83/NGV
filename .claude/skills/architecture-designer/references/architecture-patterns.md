# 후보 아키텍처 구조 목록

이 스킬의 2단계에서 사용자에게 제안할 후보 구조 목록이다. 시스템의 성격(임베디드 실시간 제어, 게이트웨이/통신 중심, 데이터 처리 중심 등)에 맞게 이 중 2~4개를 선별해 제시한다. 모든 시스템에 모든 구조가 적합한 것은 아니므로, 시스템 제약과 무관한 구조는 제안하지 않는다.

## 계층형 구조

상위 계층은 하위 계층의 서비스만 이용하고, 하위 계층은 상위 계층을 알지 못하게 계층을 나눈다(예: 응용/서비스/플랫폼/하드웨어 추상화 계층).

- 장점: 관심사 분리가 명확하고, 하위 계층(하드웨어 등) 교체 시 상위 계층 영향이 적다.
- 단점: 계층을 관통하는 기능(로깅, 진단 등)은 별도 처리가 필요하고, 계층이 많아지면 호출 경로가 길어질 수 있다.
- 적합한 경우: 하드웨어 추상화가 중요한 임베디드 시스템, 플랫폼 교체 가능성이 있는 시스템.

## 포트-어댑터(헥사고날) 구조

핵심 로직(도메인)을 중앙에 두고, 외부(센서, 통신, 저장소 등)와의 연결은 포트(인터페이스)와 어댑터(구현체)로 감싼다.

- 장점: 핵심 로직이 외부 기술/하드웨어 변경에 영향받지 않는다. 시험 시 어댑터를 모의 구현체로 대체하기 쉽다.
- 단점: 포트/어댑터 계층이 추가되어 초기 구조가 다소 복잡해 보일 수 있다.
- 적합한 경우: 알고리즘/판단 로직은 안정적이지만 주변 하드웨어·통신 방식이 자주 바뀌거나 여러 변형이 존재하는 시스템.

## 컴포넌트 기반 구조

기능 단위를 독립된 컴포넌트로 나누고, 컴포넌트는 정의된 인터페이스(제공/요구 포트)로만 연결한다.

- 장점: 컴포넌트 단위 재사용·독립 개발·독립 시험이 쉽다. AUTOSAR류 개발과도 잘 맞는다.
- 단점: 컴포넌트 수가 많아지면 통합·인터페이스 관리 부담이 커진다.
- 적합한 경우: 여러 팀이 나누어 개발하거나, 기존 컴포넌트를 재사용/교체할 가능성이 큰 시스템.

## 이벤트/발행-구독 기반 구조

컴포넌트가 서로를 직접 호출하지 않고, 이벤트를 발행하고 관심 있는 컴포넌트가 구독해 반응한다.

- 장점: 발행자와 구독자가 서로의 존재를 몰라도 되어 결합도가 매우 낮다. 구독자 추가/제거가 다른 컴포넌트에 영향을 주지 않는다.
- 단점: 이벤트 흐름이 코드만 봐서는 추적하기 어려워질 수 있어, 별도의 이벤트 흐름 문서화가 필요하다. 엄격한 실시간 순서 보장이 필요한 경우 설계가 까다롭다.
- 적합한 경우: 여러 구성요소가 상태 변화에 비동기적으로 반응해야 하는 시스템(진단, 모니터링, 다중 소비자 데이터 등).

## 파이프-필터 구조

데이터가 여러 처리 단계(필터)를 순차적으로 통과하며 변환된다. 각 필터는 입력을 받아 출력을 내는 독립된 컴포넌트다.

- 장점: 각 필터를 독립적으로 개발·시험·교체할 수 있다. 처리 순서를 바꾸거나 필터를 추가/제거하기 쉽다.
- 단점: 필터 간 상태 공유가 필요한 경우 표현이 부자연스럽다. 단계별 지연이 누적되어 실시간성에 불리할 수 있다.
- 적합한 경우: 센서 데이터 전처리→융합→판단처럼 단계적 데이터 변환이 명확한 시스템.

## 마이크로커널(플러그인) 구조

핵심(커널)은 최소 기능만 제공하고, 나머지 기능은 정의된 플러그인 인터페이스를 구현하는 확장 모듈로 추가한다.

- 장점: 핵심 안정성을 유지하면서 기능을 확장/교체하기 매우 쉽다(개방-폐쇄 원칙과 직접 부합).
- 단점: 플러그인 간 상호작용이 필요한 경우 커널을 통해 중개해야 해서 구조가 복잡해질 수 있다.
- 적합한 경우: 다양한 변형(차종/트림별 기능 차이 등)을 같은 핵심 위에서 지원해야 하는 시스템.

## 제안 시 준수 사항

- 후보마다 이 시스템의 실제 요구사항·제약(응답시간, ASIL, 팀 구조, 재사용 계획 등)을 근거로 장단점을 설명한다. 일반론만 나열하지 않는다.
- 사용자가 선택하기 전에는 특정 구조를 기본값으로 확정하지 않는다.
