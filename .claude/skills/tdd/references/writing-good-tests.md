# 좋은 테스트 작성법

> [obra/superpowers의 writing-good-tests.md](https://github.com/obra/superpowers/blob/main/skills/test-driven-development/writing-good-tests.md)를 한국어로 옮기고 Python `unittest`(`unittest.mock`)에 맞게 재구성했다.

**이 참고자료를 읽어야 하는 시점**: 테스트를 작성하거나 수정할 때, 모의객체(mock)를 추가할 때, 테스트용 정리(cleanup)/헬퍼 메서드를 추가할 때.

## 개요

테스트는 특정한 깨짐(버그)을 잡기 위해 존재한다. 아래 두 원칙이 전부를 지배한다.

```
1. 모든 테스트는 자신이 잡는 깨짐을 이름 붙일 수 있어야 한다
2. 모든 테스트는 실제 코드를 실행해야 한다
```

철저한 TDD는 이 둘을 자연스럽게 만족시킨다. 실제 코드에 대해 먼저 작성되고 실패하는 모습을 본 테스트는 이미 "실패할 수 있음"을 증명한 것이고, 실제 의존성이 느리거나 외부적일 때만 모의객체를 쓸 자격을 얻는다.

## 원칙 1: 깨짐에 이름 붙이기

테스트 본문을 쓰기 전에 먼저 답한다: **어떤 프로덕션 코드 변경이 이 테스트를 실패하게 만들며, 그 변경은 버그인가 아니면 의도적 결정인가?** 테스트는 잘못된 분기, 빠진 부작용, 잘못된 인자, 경계 조건, 깨진 계약 중 하나를 잡을 때 자신의 존재 이유를 갖는다.

**기대값은 독립적으로 도출한다.** 리터럴 값과 손으로 확인한 픽스처를 사용한다. 리터럴 `want` 값을 사용하는 표 기반(table-driven) 테스트가 선호되는 형태다. 검증 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과한다.

```python
# 잘못됨: 거울 단언 — 같은 빌더가 양쪽을 모두 계산해 항상 참이 된다
expected = buildSearchQuery({"tag": "urgent"})
self.assertEqual(buildSearchQuery({"tag": "urgent"}), expected)

# 올바름: 손으로 도출한 리터럴 값
self.assertEqual(buildSearchQuery({"tag": "urgent"}), 'tag:"urgent"')
```

**변경 감지기를 만들지 않는다.** 의도적인 결정(상수값, 정확한 메시지 문구, 내부 구조)만 실패하게 하는 테스트는 재설계할 때마다 울리고 버그가 있을 때는 잠들어 있다. 결정에 의존하는 "동작"을 테스트한다: `self.assertEqual(MAX_RETRIES, 5)`가 아니라 "실패한 호출이 5번 재시도되고 6번째 시도는 일어나지 않는다"를 검증한다.

**동작을, 텍스트가 아니라.** 스크립트/스킬/설정 파일이 특정 줄을 포함하는지 확인하는 것은 그 소스가 그 소스라는 것만 증명한다. 스크립트는 통제된 입력으로 실행하고 출력·부작용·종료코드를 검증한다.

**프레임워크가 아니라 자신의 코드를.** 자신의 코드가 경계에서 맺는 계약(등록하는 라우트, 실행하는 쿼리, 생성하는 페이로드)을 테스트한다. 업스트림(외부 라이브러리/프레임워크) 동작은 그 유지관리자가 테스트할 몫이다. 업스트림 동작이 예상과 달랐다면, 그 가정을 이름 붙인 좁은 범위의 특성화 테스트를 하나 작성한다.

### 게이트 함수

```
테스트 본문을 작성하기 전에:
  이 테스트를 실패하게 만드는 프로덕션 코드 변경을 이름 붙인다.

  이름 붙일 수 없다면            → 관찰 가능한 동작 중심으로 재설계한다
  "소스 텍스트가 바뀌었다"라면    → 산출물을 실행하고 그 효과를 검증한다
  의도적 결정만 실패하게 한다면   → 변경 감지기다. 그 결정에 의존하는 동작을 테스트한다

  기대값이 검증 대상 코드 없이 도출되었는지 확인한다.
  만약 그 코드의 로직/헬퍼를 재사용한다면:
    리터럴 값이나 손으로 확인한 픽스처로 바꾼다
```

## 원칙 2: 실제 코드를 실행하기

**모의객체는 단언의 자격이 없다.** 모의객체에 대한 단언은 모의객체가 있으면 통과하고 없으면 실패할 뿐, 실제 컴포넌트에 대해서는 아무것도 말하지 않는다. 실제 컴포넌트의 동작을 검증한다. 모의객체 자체를 검증하고 있다면, 모의객체를 걷어내거나 그 단언을 삭제한다.

```python
# 올바름: 실제 동작
self.assertTrue(response.hasHeader("X-Request-Id"))

# 잘못됨: 모의객체의 존재 확인
self.assertTrue(mockSidebar.wasCalled)
```

**올바른 수준에서 모의객체를 사용한다.** 실제 메서드를 모의객체로 바꾸기 전에 그 메서드의 모든 부작용을 먼저 파악한다. 느리거나 외부적인 연산만 모의객체로 만들고, 테스트가 의존하는 나머지는 실제로 둔다. 확신이 없으면 먼저 실제 구현으로 테스트를 실행해 실제로 무엇이 일어나는지 관찰한다.

```python
# 잘못됨: 모의객체가 중복탐지 기능이 읽는 설정 쓰기 동작을 삼켜버린다
with patch("toolCatalog.discoverAndCacheTools", return_value=None):
    ...

# 올바름: 느린 서버 기동만 모의객체로 만들고, 설정 쓰기는 실제로 둔다
with patch("mcpServerManager.MCPServerManager"):
    ...
```

**더블(테스트 대체물)을 구체적으로 만든다.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 단언한다. 아무 값이나 받아주는 페이크는 아무것도 검증하지 못한다. 각 분기(성공/오류/잘못된 형식)마다 별도의 픽스처나 스파이를 준다.

**실제 데이터를 완전히 반영한다.** 모의 데이터는 테스트가 읽는 필드만이 아니라 실제로 존재하는 문서화된 필드 전체를 모방한다. 부분적인 모의객체는 다운스트림 코드가 빠진 필드를 읽을 때 조용히 실패한다.

**프로덕션 클래스는 프로덕션 메서드만 가진다.** 테스트만 필요로 하는 정리(cleanup)는 프로덕션 클래스의 메서드가 아니라 테스트 유틸리티에 둔다. "이 메서드는 테스트에서만 호출되는가?", "이 클래스가 이 자원의 생명주기를 소유하는가?"를 자문한다. 답이 아니라면 테스트 유틸리티로 옮긴다.

**복잡한 모의객체보다 실제 컴포넌트를 우선한다.** 모의객체 준비 코드가 테스트 로직보다 커지거나, 모의객체가 실제 컴포넌트의 메서드를 놓치거나, 모의객체가 바뀔 때마다 테스트가 깨진다면, 실제 컴포넌트를 사용하는 통합 테스트로 전환한다.

### 게이트 함수

```
모의객체나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 부작용은 실제로 두고
  느리거나 외부적인 수준만 모의객체로 만든다.

  모의객체 응답은 실제 구조 전체를 반영한다.

  테스트에서만 호출되는 메서드는 테스트 유틸리티에 둔다.

  모의객체 자체를 단언하려고 하는가?
    모의객체를 걷어내거나 단언을 삭제한다.
```

## 테스트는 구현과 함께 완성된다

TDD 절차(실패하는 테스트 → 최소 구현 → 리팩터링)가 "완료"의 정의다. 그 동작이 필요로 하는 테스트만 만든다. 당연한 코드와 사람이 읽을 설명문에는 테스트가 필요 없고, 절차를 채우기 위해 쓴 테스트는 유지보수 부담만 영원히 남긴다.

## 변이 점검(Mutation Check)

끝내기 전에 프로덕션 코드를 머릿속으로 변형해 본다. 현실적인 변형마다 적어도 하나의 테스트가 실패해야 한다.

- 잘못된 상수나 인자
- 잘못된 분기 처리
- 빠진 상태 변경이나 부작용
- 비어있거나 기본값인 반환
- 0, 빈 값, None, 미인가, 잘못된 형식 입력에 대한 검증 누락

아무 테스트도 잡지 못하는 변형이 있다면, 그 동작은 보호되지 않고 있다는 뜻이거나 테스트가 항진명제(tautology)라는 뜻이다.

## 빠른 참고

| 상황 | 할 일 |
|---|---|
| 어떤 테스트든 작성할 때 | 그 테스트가 잡는 깨짐을 이름 붙인다(버그여야 하며, 결정이 아니어야 한다) |
| 기대값을 만들 때 | 손으로 도출한다. 검증 대상 코드로 계산하지 않는다 |
| 스크립트나 문서를 테스트할 때 | 실행하거나 그 소비자를 통해 압박 테스트한다. 텍스트를 grep하지 않는다 |
| 의존성에 대한 테스트를 하고 싶을 때 | 그들의 문서화된 동작이 아니라 자신의 경계 계약을 테스트한다 |
| 모의된 요소를 단언하려 할 때 | 실제 컴포넌트를 테스트하거나 모의객체를 걷어낸다 |
| 메서드를 모의객체로 만들기 전 | 그 부작용을 파악하고, 느리거나 외부적인 수준만 모의객체로 만든다 |
| 모의 응답을 만들 때 | 실제 구조를 완전히 반영한다 |
| 테스트에서만 쓰는 정리 코드가 필요할 때 | 테스트 유틸리티에 둔다 |
| 모의객체 준비 코드가 커질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환한다 |
| 테스트 파일을 끝낼 때 | 변이 점검을 수행한다 |

## 경고 신호

- 준비 코드와 단언이 같은 객체를 공유해 항상 같음이 보장됨
- 예외/충돌/셀렉터 누락으로만 테스트가 실패할 수 있음
- 의도적인 변경마다 항상 실패하고, 실수로 인한 깨짐에는 결코 실패하지 않음
- 기대값이 반복문/빌더/헬퍼 뒤에 숨겨져 있음
- 테스트가 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지만 확인함
- 프레임워크만 남아도 여전히 통과할 테스트
- 부작용이나 결과를 확인하지 않고 커버리지만을 위해 존재하는 테스트
- `*-mock` 형태의 테스트 대상을 단언하거나, 모의객체를 제거하면 실패하는 단언
- 어떤 메서드가 테스트 파일에서만 호출됨
- 모의객체 준비 코드가 테스트의 절반을 넘거나, 왜 그 모의객체가 필요한지 설명할 수 없음
- "안전을 위해" 그냥 모의객체로 만듦
