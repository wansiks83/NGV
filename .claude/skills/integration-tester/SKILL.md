# 통합시험자 (소프트웨어 통합 및 통합검증, ISO 26262 Part 6 + A-SPICE SWE.5)

## 이 스킬을 사용하는 시점

구현이 끝난 소프트웨어 컴포넌트들을 아키텍처 설계에 따라 통합하고, 통합된 결과가 아키텍처(인터페이스, 통합순서)를 만족하는지 검증할 때 사용한다.

## 0단계 — 산출물 양식 확인 (반드시 가장 먼저)

이 저장소에는 이미 실제 통합시험 양식이 있다. 임의로 형식을 만들지 않고 아래 파일을 그대로 사용한다.

- 통합전략/시험명세서: `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-001_SW 통합전략 및 통합시험 명세서 템플릿.docx` — 14개 절(목적/적용범위, 통합 원칙, 통합 항목과 순서, 환경 및 형상, 진입 및 종료 기준, 통합시험 케이스 요약, 시험 설계기법, 실행 및 결과 기록 규칙, 회귀 전략, 실패 및 편차 처리, 추적성과 보고, 적용 한계, 추적성, 참고자료) 구조를 그대로 따른다.
- 시험 케이스: `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-002_SW 통합시험 케이스 템플릿.xlsx` — 열: Test ID, Trace, Integration Item, Stimulus, Expected Result, Technique, Automation.
- 시험 결과서: `WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-003_SW 통합시험 결과서 템플릿.xlsx` — 열: Test ID, Trace, Result, Actual Result, Evidence Locator, Defect ID, Disposition.

위 경로에서 파일을 찾지 못하면 저장소 전체를 검색하고, 그래도 찾지 못하면 임의로 형식을 만들지 말고 사용자에게 요청한다.

## 1단계 — 테스트 베이시스 확인 (아키텍처 설계서)

통합시험의 **테스트 베이시스는 소프트웨어 아키텍처 설계서(SWE.2 산출물)**다. 다른 문서를 임의로 테스트 베이시스로 삼지 않는다.

- `architecture-designer` 스킬로 작성된 아키텍처 설계서에서 **인터페이스 명세**(연산, 파라미터, 사전/사후조건, 오류 처리, 시간 제약)를 모두 추출한다.
- 같은 문서의 **통합 순서**(통합 단계, 각 단계의 대상 컴포넌트, 전제조건)를 그대로 통합시험 단계 구성에 사용한다. 통합 순서를 임의로 재구성하지 않는다.
- 아키텍처 설계서를 찾지 못하면 통합시험을 설계하지 말고 사용자에게 위치를 확인한다.

## 2단계 — ISO 26262 Part 6 시험기법 선정

시험기법(무엇을 시험하는가)과 시험케이스 도출기법(어떻게 케이스를 뽑는가)을 구분해서 적용한다. 구체적인 정의와 적용 방법은 `references/iso26262-integration-test-methods.md` 참고.

- **시험기법**: 요구사항기반시험, 인터페이스시험, 결함주입시험, 자원사용시험, (해당 시) 모델-코드 백투백비교시험 중 이 통합 단계에 적용할 것을 선정하고 근거를 남긴다.
- **케이스 도출기법**: 공용 스킬 `test-design-techniques`의 카탈로그에서 인터페이스 계약의 성격에 맞는 것을 선택한다(함수 계약의 사전조건 → 경계값분석/사전조건·사후조건검증, 정책 의사결정표 → 의사결정표기반, 상태전이표 → 상태전이기반). 기법 정의는 이 스킬에서 다시 설명하지 않는다.

## 3단계 — 통합 순서에 따른 시험 단계 설계 (양식 3~5절)

- 아키텍처 설계서의 통합 순서를 그대로 시험 단계로 옮긴다. 각 단계마다 통합 대상 컴포넌트, 전제조건(선행 단계 완료, 필요한 스텁/드라이버), 진입/종료 기준을 정의한다.
- 통합 순서에 순환 의존이 있었다면(아키텍처 단계에서 걸러졌어야 함) 통합시험을 설계하지 말고 먼저 아키텍처를 재검토하도록 안내한다.

## 4단계 — 인터페이스 기반 시험 케이스 설계 (양식 6~7절)

- 아키텍처 설계서의 **모든 인터페이스**(제공/요구 인터페이스 각각)에 대해 최소 1개 이상의 시험 케이스를 설계한다. 빠진 인터페이스가 없는지 점검한다.
- 각 시험 케이스는 `TPL-SWE5-002` 양식의 열(Test ID, Trace, Integration Item, Stimulus, Expected Result, Technique, Automation)에 맞춰 작성한다. `Trace`에는 인터페이스 ID와 관련 소프트웨어 요구사항 ID를 함께 기록한다.
- 결함주입시험과 자원사용시험의 구체적 설계 방법은 `references/fault-injection-and-resource-tests.md` 참고.
- 코드로 구현하는 통합시험은 `tdd` 스킬의 절차와 테스트 함수 Doxygen 주석 규칙(`@brief`/`@technique`/`@case`)을 그대로 따른다. 다만 통합시험은 실제 컴포넌트를 연결해 실행하는 것이 목적이므로, 단위시험처럼 의존성을 모의객체로 대체하지 않는다(느리거나 외부적인 것만 예외).

## 5단계 — 함수커버리지·콜커버리지 100% 달성 (필수, 오픈소스 도구로 실측)

- **함수커버리지**: 통합시험 실행 중 아키텍처의 모든 인터페이스 연산(함수)이 최소 1회 호출되었는지 확인한다.
- **콜커버리지**: 아키텍처/상세설계에 정의된 모든 호출 관계(호출 지점)가 통합시험 중 최소 1회 실행되었는지 확인한다.
- 두 지표 모두 **100%**를 목표로 하며, 추정이 아니라 도구로 실측한다. 측정 방법은 `references/coverage-measurement.md` 참고.
- 100%에 도달하지 못하면 "완료"로 보고하지 않는다. 시험 케이스를 보강해 커버되지 않은 함수/호출을 없애거나, 정말로 도달 불가능한 경우(예: 방어적 코드, 도달 불가능한 예외 경로)에는 그 이유를 근거와 함께 사용자에게 보고하고 승인을 받는다. 임의로 기준을 낮추지 않는다.

## 6단계 — 실행, 회귀, 실패/편차 처리 (양식 8~10절)

- 시험 실행 결과를 `TPL-SWE5-003` 양식(Test ID, Trace, Result, Actual Result, Evidence Locator, Defect ID, Disposition)에 기록한다.
- 컴포넌트나 인터페이스가 변경되면, 변경 영향을 받는 통합시험을 회귀 대상으로 다시 실행한다.
- 시험 실패는 원인을 분류(코드 결함/시험 설계 오류/환경 문제)하고, 결함으로 판정되면 결함 ID와 연결한다.

## 7단계 — 추적성, 적용 한계, 산출물 정리 (양식 11~14절)

- 아키텍처 인터페이스 ↔ 시험 케이스 ↔ 실행 결과 ↔ 결함 간 양방향 추적표를 작성한다.
- 이 통합시험(PC/SIL·Web 수준 등)으로 확인하지 못하는 범위(HIL, 실차, 시스템 시험 등)를 적용 한계에 명시한다.
- 최종 산출물은 `TPL-SWE5-001/002/003` 양식의 구조를 그대로 따른다.

## 원칙 요약

- 테스트 베이시스는 항상 아키텍처 설계서의 인터페이스와 통합 순서다. 임의의 순서나 임의로 만든 인터페이스로 시험하지 않는다.
- 함수커버리지·콜커버리지 100%를 실제 도구로 확인하기 전에는 통합시험을 완료로 보고하지 않는다.
- 통합시험은 실제 컴포넌트로 실행한다. 모의객체는 느리거나 외부적인 의존성에만 최소한으로 사용한다.
