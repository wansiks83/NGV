# SW 시스템(자격) 테스트 케이스 생성 — A-SPICE SWE.6

## 개요

SW 요구사항 명세서(SWE.1 산출물)를 근거로 SW 시스템(자격) 테스트 케이스를 생성하는 방법론이다. 이 스킬은 "무엇을 근거로, 어떤 원칙으로" 테스트 케이스를 설계할지만 정의한다. 요구사항 분석, 사용자와의 확인, 실제 산출물 작성은 이 스킬을 사용하는 `sw-system-tester` 서브에이전트가 수행한다. A-SPICE SWE.6 BP/산출물 요약은 `references/aspice-swe6.md` 참고.

## 0단계 — 산출물 양식 확인 (반드시 가장 먼저)

이 저장소에는 이미 실제 SW 검증(자격시험) 양식이 있다. 임의로 시트 구조를 만들지 않고 아래 파일을 그대로 사용한다.

- 검증 명세서: `WP_Templates/Engineering/SoftwareVerification/TPL-SWE6-001_SW 검증 명세서 템플릿.xlsx` — 시트 구성: "SW 요구 기반 검증 명세"(열: Test ID, SW Req, Level/Environment, Stimulus, Expected Result, Technique, Execution), "SW 검증 환경 및 제한"(환경 ID, 구성, 버전 및 식별, 사용 범위, 수집 증거, 명시적 제외), "변경 이력".
- 검증 결과서: `WP_Templates/Engineering/SoftwareVerification/TPL-SWE6-002_SW 검증 결과서 템플릿.xlsx` — 시트 구성: "SW 요구 기반 검증 결과"(열: Test ID, SW Req, Result, Actual Result, Evidence Locator, Execution Time, Scope Note), "SW 검증 결과 요약"(항목, 계획, 실행, Pass, Fail, 미실행, 판정, 제한), "변경 이력".

**기능/비기능 요구사항 구분은 별도 시트가 아니라 같은 "SW 요구 기반 검증 명세" 시트 안에서 `SW Req`(추적 대상 요구사항 ID)로 구분한다.** 비기능 요구사항에 대한 케이스는 `Technique` 열에 적용 기법과 함께 해당 ISO 25010 품질특성을 표기해 그룹으로 식별할 수 있게 한다(예: `경계값분석 / 성능효율성`). 위 경로에서 파일을 찾지 못하면 저장소 전체를 검색하고, 그래도 찾지 못하면 임의로 형식을 만들지 말고 사용자에게 요청한다.

## 1단계 — 테스트 베이시스 확인 (SW 요구사항 명세서)

- 테스트 베이시스는 `requirements-analyst` 스킬로 작성된 **SW 요구사항 명세서(SWE.1 산출물)**다. 명세서에 실제로 기술된 내용에만 근거해 테스트 케이스를 작성한다. 명세서에 없는 내용을 임의로 추측해 작성하지 않는다.
- 요구사항을 기능(FR)/비기능(NFR)으로 구분한다. 비기능 요구사항의 품질특성 분류는 `requirements-analyst` 스킬의 `references/iso25010-nfr.md`에 정의된 ISO 25010 8개 품질특성/부특성을 그대로 따른다. 이 스킬에서 그 분류를 다시 정의하지 않는다.
- 요구사항 자체가 모호하거나 해석의 여지가 있으면 임의로 판단하지 말고 사용자에게 확인한다.

## 2단계 — 시험 케이스 도출 기법 선정

- 케이스 도출 기법(경계값분석/동치분할/조합테스트/페어와이즈/엣지케이스/경험기반 등)과 페어와이즈·전수조합 생성을 위한 PICT 도구 사용법은 공용 스킬 `test-design-techniques`를 그대로 따른다. 이 스킬에서 기법을 다시 정의하지 않는다.
- ISO 26262 Part 6 관점에서, ASIL이 할당된 요구사항은 판정기준의 전 분기(경계값, 조건 조합)를 빠짐없이 검증해야 한다(`test-design-techniques`의 조합테스트/경계값분석을 우선 적용).
- ISO 29119/ISTQB의 용어 체계(긍정/부정 분류 등)를 근거로 각 케이스를 분류한다.
- 기법 선택이나 커버리지 범위 설정이 판단하기 어려운 경우 임의로 결정하지 말고, `sw-system-tester` 에이전트를 통해 사용자 확인을 받는다.

## 3단계 — 테스트 케이스 작성 원칙

- 기능 요구사항과 비기능 요구사항 모두 테스트 케이스는 최소한 다음을 포함한다: Test ID, SW Req(추적 대상), Level/Environment, Stimulus(입력), Expected Result(예상 결과), Technique(사용 기법, 비기능은 품질특성 포함), Execution(실행/자동화 방법).
- 테스트의 예상 결과를 임의로 가정하지 않는다. 명세서에 근거가 없다면 `sw-system-tester` 에이전트가 사용자에게 확인을 받아야 한다.
- 요구사항 명세서 원문에 없거나 원문보다 엄격한 판정기준을 사용자 확인을 거쳐 확정한 경우, 그 근거(확정 일자, 승인 주체)를 산출물에 함께 기록한다(양식에 별도 열이 없으면 `Scope Note`/비고성 열에 기록).
- 명세서에 직접적 근거는 없으나 QA 관점에서 추가를 제안하는 테스트 케이스는 Test ID 또는 명칭 끝에 "(제안)"을 표기해 구분한다.
- 의미 없이 테스트 커버리지 수치 달성만을 목적으로 하는 케이스는 만들지 않는다.
- 실행자가 그대로 재현할 수 있는, 실행 가능한 테스트 케이스만 작성한다.
- 프로젝트에서 정한 테스트 커버리지 목표(예: CLAUDE.md에 명시된 기준)를 준수한다.

## 4단계 — 추적성 및 결과 기록

- SW 요구사항 ↔ 테스트 케이스 ↔ 실행 결과 간 양방향 추적을 확보한다(필요 시 `TPL-TRC-001` 양방향 요구사항 추적 매트릭스와 연결).
- 실행 결과는 `TPL-SWE6-002` 양식에 기록한다.
