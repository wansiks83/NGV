# 상세설계자 (소프트웨어 상세설계/유닛 구현, ISO 26262 Part 6 + A-SPICE SWE.3)

## 이 스킬을 사용하는 시점

소프트웨어 아키텍처(SWE.2 산출물)를 구현 가능한 단위(모듈/함수/클래스)로 상세화하거나, 기존 상세설계를 응집력/결합도/SOLID/ISO 26262 코딩 제약/추적성 관점에서 점검·보완할 때 사용한다.

## 0단계 — 산출물 양식 확인 (반드시 가장 먼저)

이 저장소에는 이미 실제 상세설계 양식이 있다. 임의로 형식을 만들지 않고 아래 파일을 그대로 사용한다.

- 본문 양식: `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SWE3-001_SW 상세설계서 템플릿.docx` — 15개 절(목적/적용범위, 모듈 분해, 상세 호출관계, 공통 자료형, 핵심 함수 계약, 핵심 알고리즘, 정책 의사결정표, 상태전이 상세, Web 및 API 상세, 오류와 방어 동작, 코딩 및 검증 규칙, 단위와 요구사항 할당, 구현 경계, 추적성, 참고자료) 구조를 그대로 따른다.
- 다이어그램 양식: `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SWE3-002_상세설계 UML 및 호출관계 템플릿.drawio` — 구현 단위/책임, 함수·클래스 호출, 입출력 자료형, 설계·시험 추적 ID를 표현한다.
- Python 오픈소스 의존성이 있는 프로젝트라면: `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SBOM-001_Python 의존성 SBOM FOSS 라이선스 목록 템플릿.xlsx`도 함께 채운다(`references/sbom-foss-guide.md` 참고).

위 경로에서 파일을 찾지 못하면(이동·삭제된 경우) 저장소 전체를 검색하고, 그래도 찾지 못하면 임의로 형식을 만들지 말고 사용자에게 요청한다.

## 1단계 — 입력 확인

- 소프트웨어 아키텍처 설계서(SWE.2 산출물: 컴포넌트, 인터페이스, 통합 순서)와 소프트웨어 요구사항(SWE.1 산출물)을 확인한다.
- 대상 컴포넌트의 ASIL을 확인한다(코딩 수준 제약의 엄격도가 ASIL에 따라 달라진다).

## 2단계 — 모듈 분해 (양식 2절)

- 아키텍처 요소를 구현 가능한 단위(모듈/클래스/함수 그룹)로 분해한다.
- 각 단위에 ID, 책임, 소스 위치(예정 경로)를 부여한다.
- **응집력·결합도·SOLID 원칙은 컴포넌트 수준에서 유닛 수준으로 그대로 이어진다.** `architecture-designer` 스킬의 `references/cohesion-coupling.md`, `references/solid-principles.md`를 그대로 읽고 유닛 단위에 적용한다(하나의 유닛은 하나의 책임만 가지며, 유닛 간 결합은 인터페이스를 통한 데이터 결합만 허용한다).

## 3단계 — 상세 호출관계 (양식 3절, 다이어그램)

- 함수/클래스 간 호출 순서와 의존 방향을 `TPL-SWE3-002` 드로우아이오 양식에 작성한다.
- 호출 관계에 순환 의존이 없는지 확인한다(있으면 2단계로 돌아가 재분해한다).
- 필요 시 `requirements-analyst` 스킬의 `references/uml-sysml-guide.md`에 있는 시퀀스/상태기계 다이어그램 기법을 유닛 수준 호출관계에도 적용한다.

## 4단계 — 공통 자료형 (양식 4절)

- 공통 데이터 구조, 열거형, 단위, 유효 범위, 불변조건, 직렬화 규칙을 정의한다.
- ISO 26262 코딩 수준 제약(강한 타입 지정 등)을 반영한다. `references/iso26262-swe3-constraints.md` 참고.

## 5단계 — 핵심 함수 계약 (양식 5절, 필수)

- **모든 유닛 간 통신은 함수/인터페이스 계약을 통해서만 이루어진다.** 다른 유닛의 내부 변수·자료구조를 직접 참조하지 않는다.
- 각 함수 계약에는 입력, 출력, 사전조건, 사후조건, 부작용, 예외/오류 처리, 시간 제약을 명시한다. 작성법과 예시는 `references/function-contract-guide.md` 참고.

## 6단계 — 핵심 알고리즘 / 정책 의사결정표 / 상태전이 상세 (양식 6~8절)

- 알고리즘은 의사코드 또는 흐름도로 처리 순서·판단 조건·경계값을 작성한다.
- 조건 조합에 따라 동작이 갈리는 로직은 정책 의사결정표로 작성한다.
- 상태 기반 동작은 상태 저장 위치, 전이 함수, 이벤트, 가드, 타이머, 초기화 동작까지 상세히 기술한다.
- 표기법과 작성 규칙은 `references/unit-design-techniques.md` 참고.

## 7단계 — Web 및 API 상세, 오류와 방어 동작 (양식 9~10절)

- 해당하는 경우 엔드포인트, 요청/응답 구조, 검증, 오류 코드, 보안 경계를 정의한다.
- 유효하지 않은 입력, 예외, 자원 실패에 대한 검출·처리·기록·복구(방어적 설계)를 기술한다. ASIL이 있는 유닛은 `references/iso26262-swe3-constraints.md`의 방어적 설계 원칙을 반영한다.

## 8단계 — 코딩 및 검증 규칙, 단위/요구사항 할당, 구현 경계 (양식 11~13절)

- 코딩 표준, 정적분석 규칙, 단위검증 기준(커버리지, 리뷰 기준)을 정의한다. 이 결과는 이후 SWE.4(소프트웨어 유닛 검증)의 입력이 된다.
- 구현 단위를 아키텍처 요소, 소프트웨어 요구사항, 단위시험에 연결한다.
- 생성 코드, 외부 라이브러리, 플랫폼 종속부, 구현하지 않는 범위(구현 경계)를 명시한다. 외부/오픈소스 라이브러리가 있다면 `references/sbom-foss-guide.md`에 따라 SBOM/FOSS 검토를 함께 진행한다.

## 9단계 — 추적성 및 산출물 정리 (양식 14~15절)

- 아키텍처 요소 ↔ 상세설계 ↔ 소스 파일/함수 ↔ 단위시험 간 양방향 추적표를 작성한다.
- `TPL-SWE3-001` 양식의 절 순서와 표기법을 그대로 따라 최종 산출물을 정리한다.

## 원칙 요약

- 유닛 간 통신은 반드시 정의된 함수 계약(인터페이스)을 통해서만 이루어진다.
- 응집력·결합도·SOLID 원칙 위반이 발견되면 다음 단계로 넘어가기 전에 모듈 분해를 재검토한다.
- ASIL이 부여된 유닛에는 해당 ASIL에 맞는 코딩 수준 제약(포인터/동적메모리/전역변수/인터럽트/무조건 분기 제한)을 명시적으로 반영한다.
